## 01. 产品定义与功能边界

### 1.1 核心体验

玩家是生活在一个自主运转的虚构古代中国世界中的真实角色，而不是全知全能的战略地图观察者。玩家可选择雇佣兵、商人、冒险者、领主或统治者路线；通过亲自作战、经营、结交、征募与政治决策改变局势。世界中的其他家族、领主和势力具备独立目标与资源约束，即使玩家不参与，战争、经济和人物关系也应持续演化。

四个设计支柱：个人动作战斗（技巧与装备并重）、军队实时指挥（编队协同与地形）、持续世界模拟（资源与势力演化）、长期角色与家族发展（身份与传承）。任何新功能须说明它与四个支柱中的哪一个相连，避免形成互不关联的小游戏集合。

### 1.2 游戏模式

| ID | 模式 | 功能范围 | 交付 |
|---|---|---|---|
| MOD-01 | 剧情战役 Campaign | 角色创建、序章教程、家族事件、主线阶段、分支目标、失败/继续沙盒 | MUST |
| MOD-02 | 自由沙盒 Sandbox | 可选开局、世界种子、配置规则、动态事件与自由发展，无强制主线 | MUST |
| MOD-03 | 自定义战斗 Custom Battle | 地图、天气、时段、双方兵种构成、人数、指挥者、野战/攻城及战斗难度 | MUST |
| MOD-04 | 多人竞技 Multiplayer | 匹配/服务器列表、遭遇、团队死亡竞赛、队长、攻城、决斗等规则；与单人共享动作战斗 | MUST |
| MOD-05 | 内容扩展 Modding | 配置、地图、任务、兵种、装备、规则插件、编辑与验证工具 | MUST |
| MOD-06 | 海战扩展 Naval | 水域大地图、舰船、舰队、海战、登船、沿岸袭击、自定义海战 | EXT |

本体覆盖完整陆地战役与多人系统；海战是独立的完整扩展规格（第24章），不作为海上联机或单人联机战役的默认承诺。若产品要求与特定版本逐条一致，应建立逐版本功能差异清单；本文参考公开产品说明及更新资料，额外提供高级开局、场景修饰器、家族仇怨、队伍控制等扩展性设计。

### 1.3 内容规模与品质目标（原创设计目标，不是原作统计）

| 内容 | 最终规划基线 | 质量约束 |
|---|---:|---|
| 大陆文化 / 初始王国 | 6–8 种 / 8–10 个 | 地貌、建筑、装备、兵种、经济与政治有差异 |
| 城镇 / 城堡 / 村庄 | 50–70 / 80–120 / 200–350 | 每个领地有归属、生产、交通、守军与可访问场景 |
| 家族 / 具名英雄 | 80–130 / 500–1000 | 有谱系、角色、关系和决策能力，允许动态增减 |
| 兵种与成长节点 | 150–250 | 文化树、普通/贵族兵、装备角色差异、无循环升级 |
| 地图/场景族 | 6–10 地貌族及文化建筑族 | 野战、城镇、村庄、城堡、藏身处、竞技场、室内等具备完整玩法标记 |
| 同屏战斗实体 | 默认目标 500，压力目标 1000 人形战斗单位 | 骑乘坐骑、弹体、尸体等额外纳入性能预算；以实测确定硬上限 |
| 任务模板 / 主线 | 30–50 动态模板及完整主线 | 多条件、多结果、替代完成和失效处理 |
| 战役时长 | 可持续数十至数百小时 | 长期存档、人口传承、经济稳定、势力可消亡与重组 |

数量不代表质量完成；具体地图、资产与文本在内容计划中细化。玩家可调整战斗规模；内容规模需要兼顾人力预算，设计上不写死数量上限。

### 1.4 难度与可访问性

战斗 AI 技巧、玩家及友方承伤、战役死亡/继承、战场规模、经济与战略压力分别配置。难度不依靠 AI 无限资源或全图透视；必要的加成应明确标识。支持按键重映射、手柄、字幕、字号、色盲可区分阵营、镜头晃动与血腥表现开关、教学重看。允许单人退出与安全点存档，铁人模式作为规则选项。多人规则不可被客户端难度覆盖。

## 02. 玩法循环、玩家路径与游戏状态

### 2.1 三层时间尺度

```mermaid
flowchart TD
    A[创建角色与世界] --> B[战略地图: 旅行/探索/贸易]
    B --> C[城镇/村庄: 招募/任务/互动]
    C --> B
    B --> D[遭遇/攻城: 决定行动]
    D --> E[部署与实时战斗]
    D --> F[自动结算/谈判/撤离]
    E --> G[伤亡/俘虏/战利品/影响力]
    F --> G
    G --> H[成长/经营/家族与外交]
    H --> B
    H --> I[继承/退休/王国兴亡]
    I --> B
```

短循环（秒到分钟）：观察、移动、方向攻击/格挡、战场命令、阵型调整、受击反馈。中循环（分钟到小时）：行军、侦察、招募、训练、交易、任务、遭遇与整备。长循环（小时到多日游戏时间）：积累财富和名望、建立家族、加入势力、管理封地、参与政治、继承与统一或其他自主目标。各循环通过共享经济、伤亡、关系和成长状态形成因果闭环。

### 2.2 玩家身份与可达性

平民/冒险者可以交易、完成任务、招兵、参加竞技；达到名望条件成为受雇佣兵；满足家族等级与政治关系成为封臣；获得领地或通过政治程序建立王国；成为统治者可参与政策、外交和封地分配。身份不是硬编码的线性关卡，允许脱离、投诚、失势、叛变、被俘、逃脱和继承。商贸、竞技、雇佣军及政治路线应能分别维持资源循环。

### 2.3 全局状态机

```mermaid
stateDiagram-v2
    [*] --> Boot
    Boot --> Frontend
    Frontend --> NewWorld
    Frontend --> LoadWorld
    Frontend --> CustomSetup
    Frontend --> MultiplayerLobby
    NewWorld --> CampaignMap
    LoadWorld --> CampaignMap
    CampaignMap --> Encounter
    Encounter --> CampaignMap
    Encounter --> LoadingMission
    CampaignMap --> LoadingMission: 访问场景
    CustomSetup --> LoadingMission
    MultiplayerLobby --> LoadingMission
    LoadingMission --> Mission
    LoadingMission --> Recovery: 加载失败
    Mission --> Results
    Results --> CampaignMap: 战役/访问
    Results --> CustomSetup: 自定义
    Results --> MultiplayerLobby: 多人
    Recovery --> Frontend
    CampaignMap --> Frontend: 安全退出
```

状态由 `GameSession` 管理，UI 不直接换场或提交结果。加载使用可取消资源任务；失败恢复至进入前检查点，释放所有临时租约和资源。暂停区分模拟暂停、UI 暂停、联网不可暂停。地图时间在关键战斗/菜单中冻结；其他场景时间流逝采用明确规则，不让世界在后台无约束地更新。访问场景也使用 Mission 容器，不能把所有 Mission 都视为战争。

## 03. 总体软件架构

### 3.1 架构原则

选用**模块化单体 + 双仿真运行时 + 数据驱动 + 热路径数据导向 + 可组合规则**。单人无需微服务、全局分布式事务或消息中间件；多人后端按独立部署能力拆分。以战役领域、任务场景领域、联网会话为独立边界，基础设施依赖通过接口反转。世界持久化对象与战场临时对象分离；不能把每名战役士兵都作为长期运行的引擎节点。

```mermaid
flowchart TB
    UI[表现层: UI/输入/相机/声音/渲染代理]
    APP[应用层: GameSession/UseCases/CommandRouter]
    UI --> APP
    APP --> C[Campaign Runtime]
    APP --> M[Mission Runtime]
    APP --> N[Network Session]
    N --> M
    C <-->|EncounterSpec / MissionResult| M
    C --> R[领域规则: Character/Economy/Politics/Army]
    M --> B[战场规则: Combat/Formation/Objective/AI]
    R --> D[定义数据与公共值类型]
    B --> D
    C --> P[端口: 存档/时钟/日志/随机/资源]
    M --> P
    N --> P
    I[适配器: 引擎/文件/平台/网络] -.实现.-> P
    T[编辑器与构建工具] --> D
```

图中的 Campaign ↔ Mission 表示数据契约，不表示相互引用内部类。真实跨域调用由应用层协调，`contracts` 只含值对象与接口，无可变世界实体。

### 3.2 领域模块与写权限

| 模块 | 负责的权威数据与行为 | 依赖或接口 |
|---|---|---|
| Core/Session | 启停、世界/任务生命周期、依赖装配、场景状态 | Ports、Contracts |
| World/Clock | 地图位置、日历、天气、地形/交通、模拟调度 | 地图定义、随机流 |
| Character | Hero、属性、技能、成长、伤病、死亡 | 人物定义、成长规则 |
| Clan | 家族成员关系、婚姻谱系、领导继承、名望与资产归属 | Character、政治/财务命令 |
| Party/Army | 编制、兵力、俘虏、库存引用、补给、联盟军团 | Character、Inventory、World 查询 |
| Inventory/Ledger | 物品与数量、金钱账户、交易流水、仓储 | ItemDef、Transaction |
| Economy | 生产、需求、市场报价、商队、工坊经营 | Ledger、World、Settlement 查询 |
| Settlement | 领地归属、驻军引用、繁荣、治安、忠诚、建设 | Party、Ledger、政治授权 |
| Politics/Diplomacy | 王国成员、战争和平、投票、政策、封地决议 | Clan、Settlement、Ledger 命令 |
| Quest/Dialogue | 任务实例、条件、对话流程、场景交互流程 | 只读世界投影、用例端口 |
| StrategicAI | 领主、队伍、王国的意图和行动计划 | WorldSnapshot、合法命令 |
| Encounter | 参与方、遭遇状态、兵力预留、任务结果提交 | Campaign 各领域用例、Mission 契约 |
| Mission | 战场/访问场景实体、队伍、规则、波次和结果记录 | 战场规则与输入契约 |
| Combat | 运动意图校验、装备切换、攻击、命中、生命与战场状态 | Agent 状态存储、碰撞查询 |
| Formation | 编队成员、阵型槽位、命令、队形、控制权 | Mission、移动/导航 |
| BattlefieldAI | 战术计划、编队行为、个体动作意图 | 只读战场快照、命令接口 |
| Navigation/Movement | 地图/局部查询、路径缓存、速度、碰撞与位姿 | 地形、动态障碍、引擎适配器 |
| Presentation | UI 状态、镜头、动画、特效、音效、输入翻译 | Commands、ReadModels、ViewEvents |
| Persistence/Content | 快照编解码、迁移、数据包、资源引用和校验 | 版本化契约、文件端口 |
| Multiplayer | 鉴权、会话、命令传输、复制、匹配、服务器管理 | Mission、网络端口 |

**所有权规则：**一个事实只能有一个权威写入模块。经济模块不得直接更改家族金钱，必须请求账本；任务系统不能直接改领地归属，必须走政治/遭遇用例；AI 不能直接修改敌军或绕过命令校验；表现层不写权威数据。跨模块的一致性操作由应用层事务协调。查询允许通过只读门面/不可变快照完成，严禁复制出第二套可写权威状态。

### 3.3 命令、查询、事件与规则接口

- Command：表达意图（如 `BuyGoods`、`IssueFormationOrder`、`ProposePeace`）；含命令 ID、发起人、期望版本、时间/序号、参数。处理器鉴权、校验、执行并返回明确成功/错误；失败不得产生半完成状态。
- Query：只读数据（如 `GetMarketQuote`、`GetVisibleEnemies`），不改变游戏结果、不触发隐式时间推进。
- DomainEvent：提交成功之后才发布的业务事实（如 `GoodsTraded`、`HeroDied`）。低频跨模块通知可订阅；需要一致性的写入必须在事务中完成，不能等待多个任意顺序监听者补齐。
- Simulation Intent：高频轻量数据（移动、攻击、目标）；固定容量数组/队列批量提交，禁止每帧为每士兵广播重量级全局事件。
- Rule/Policy：可替换的纯计算规则（报价、伤害、经验、军饷、战术评分），输入快照与配置，输出值及分项解释，不直接修改领域对象。

```text
ICommandHandler<C, R>.execute(command, transaction) -> Result<R, DomainError>
IQueryHandler<Q, R>.query(query, read_context) -> R
IRule<I, O>.evaluate(input, config, random_stream?) -> O
ISimulationSystem.step(tick, snapshot, command_buffer) -> SystemOutput
IEventSubscriber<E>.on_committed(event, read_context) -> FollowUpCommands
```

错误统一 `InvalidArgument/Unauthorized/InsufficientResource/InvalidState/StaleVersion/NotFound/Conflict/Unavailable`。业务事件明确阶段与顺序；监听产生的命令进入下一受控阶段，并设置递归/预算上限。UI 动画和遥测监听可丢弃，不参与游戏真值。

### 3.4 多运行时与生命周期

`CampaignRuntime` 持有长期世界状态，地图单位多为数据记录；`MissionRuntime` 持有局部高频状态，支持野战、攻城、访问、竞技、任务、多人规则；两者都依赖可独立运行的模拟核心。`NetworkSession` 负责命令和状态复制，不另写一套战斗规则。进程内单人使用 LocalAuthority，多人由 DedicatedAuthority 接管。一个单人会话同时只允许一个交互任务；远方非玩家遭遇走轻量自动仿真。客户端视觉实例可重建，不作为存档依据。

## 04. 战略世界与时间系统

### 4.1 世界模型

大陆由地形栅格/导航多边形、交通图、行政区域和地点构成。位置使用世界地图坐标（单位约定独立于战场米制坐标）；交通包含道路、山口、桥梁和水域，港口留作扩展。战略地图支持旋转、缩放、选中实体、路径预览、图标聚合、昼夜与季节。地理逻辑数据和显示模型独立。村庄关联市场城镇，城堡/城镇关联封地与文化；所有关系以 ID 引用。

地图移动速度由基础兵种构成、骑乘/驮畜、载重、地形、天气、士气、技能、伤兵、俘虏与队伍规模影响；乘积采用限幅，防止超载负速度。`speed = clamp(base * terrain * weather * burden * mount * morale * skill, min, max)`。路径使用图搜索/多边形路径，局部移动检测障碍；路径因战争边界、桥梁或目标变化失效时重算。队伍间拦截使用连续/扫掠距离检测，避免加速跳过遭遇。

### 4.2 时钟和更新计划

模拟以整数游戏分钟作为战略时间，不依赖真实帧率；速度档位转换每秒推进的分钟数。关键事件边界不能被快进跳过。暂停停止战略时间。固定排序与独立随机流保证相同版本、种子、输入的纯领域规则可重复；不宣称所有物理和引擎浮点跨平台位级确定。

| 更新相位 | 建议频率（游戏时间） | 规则 |
|---|---|---|
| 位置/近距离遭遇 | 1–5 分钟步进（必要时细分） | 移动、碰撞式接触、可见信息更新 |
| 队伍行为与路径 | 10–60 分钟或关键事件 | 执行目标、补给检查、拦截、返回驻地 |
| 战略规划 | 1–6 小时，错峰 | 候选行动评分、军团目标、商队路线 |
| 消耗与生产 | 每日分相 | 粮耗、工资、产出、市场、税收、驻军、忠诚 |
| 家族与政治 | 每日/每周及事件 | 关系、投票、婚育、继承、王国政策 |
| 长期统计 | 每周/季节/年 | 报表、世界衰亡检查、人口与内容调节 |

日结固定为：基础生产/消费计划 → 校验库存及账务 → 市场/经营更新 → 队伍补给/薪资 → 领地变量 → 政治/AI 计划 → 日终事件。经济与政治依赖按快照阶段读取，防止因循环遍历顺序导致同日因果漂移。日结预算超限则分批完成并禁止显示部分已提交快照；队伍的真实日消耗不可被重复运行。

### 4.3 世界信息与遭遇

每支队伍具备发现半径，受地形、昼夜、侦察技能与目标规模影响；对不可见实体只保留过期情报。地图标记区分已知/最后看到/传闻。敌对队伍接触后由 Encounter 用例预留参战方，创建遭遇；非敌对可交流、交易、招募/俘虏交换或离开。强盗、商队、村民、家族队伍、军团与藏身处采用数据配置和独立行为。生成系统依据地区治安、密度和再生冷却控制数量，不无限刷新。动态战争会切断贸易与人员流动。

### 4.4 验收

`WLD-01` 地图寻路与拦截在三档速度、暂停恢复及地形变化下成立；`WLD-02` 日结无重复且确定顺序；`WLD-03` AI 不可读取超出许可的情报；`WLD-04` 远方世界持续演化、访问场景和遭遇切换不丢失进度；`WLD-05` 相同版本种子生成可验证一致的初始世界。

## 05. 人物、技能、家族与长期成长

### 5.1 人物分类和创建

`Hero` 为具名持久人物，有唯一身份、外观、出身、文化、特质、技能、关系、所属家族、财务/装备引用、当前位置与生命状态。普通兵用 `TroopDef + RosterEntry` 聚合，不强制每人有长期人物记录。战斗中两者均实例化为 `AgentId`，英雄保留 HeroId 映射。玩家与 NPC 共用成长与生死规则，玩家输入只是控制器差异。

角色创建：选择文化、年龄/背景、外观、童年/职业经历、初始技能/装备、开局身份、家族旗帜。属性影响学习效率及特定能力；技能以使用获取经验；专精点和属性共同影响学习速度与软上限。经验记录按实际行为结算，重复无风险行为收益衰减；等级、技能、天赋效果分别定义，避免同一经验重复发放。

六类属性建议：力量/控制/耐力/灵巧/社交/智识；覆盖单手、双手、长杆、弓、弩、投掷、骑术、跑动、锻造、侦察、战术、游荡/潜行、魅力、领导、贸易、管理、医术、工程等技能。具体名称、成长曲线、天赋分叉均采用原创设计。天赋带作用域（自身、队长、队伍、军团、领地、家族）及堆叠规则；同类加成使用统一计算顺序，带来源解释。

### 5.2 家族与伴侣

家族维护成员、领导者、文化、旗帜、名望、等级、封地、队伍与工坊权益。名望来自战斗、任务、竞技和政治成就；影响同伴/队伍/政治资格。关系是有向或对称类型明确的记录（友情、敌对、亲属、债务等），不把婚姻或战争关系混用一个数值。

酒馆等地可招募同伴，配置装备、技能、队长、总管、侦察、军医、工程、总督或商队领导；同一时间同一人物只能担任允许并存的角色，角色能力按范围生效。支持婚姻提议、配偶加入、子女成长、成年教育、自然老化、战斗死亡、退休、囚禁与继承。谱系禁止循环；婚配应遵循成年与亲缘限制。玩家角色死亡或退休可选择合法继承人继续；无继承人时触发清晰结束/另起角色规则。原本角色资产依归属规则继承，而不是无条件复制装备与物品。

### 5.3 装备与伤病

角色装备槽分战斗/便装配置，校验武器、护甲、坐骑、马具的兼容性与使用要求。英雄受伤后按医术和休养恢复，不能重复进入战斗；致命与非致命状态区分，死亡概率受规则配置并记录结算原因。NPC 个性（勇敢、谨慎、仁慈、贪婪、荣誉等）用于决策评分及对话，不直接决定一切行为。

### 5.4 验收

`CHR-01` 创建与技能使用、升级、天赋互斥/作用域正确；`CHR-02` 装备合法且库存守恒；`CHR-03` 伤病、囚禁、死亡与恢复不产生重复身份；`CLN-01` 家族等级与角色任命约束；`CLN-02` 婚育、成年教育、继承及家族消亡可连续运行多年；`CLN-03` 玩家换代后任务、军队、封地与关系按规则迁移。

## 06. 队伍、军团、兵种、库存与后勤

### 6.1 定义和运行对象

`TroopDef` 描述文化、等级、职责（步兵/远程/骑兵/骑射等）、技能模板、装备池、升级边、招募/工资与经验曲线。升级图为有向无环图，升级必须满足经验、金钱、马匹/装备等可配置条件。招募来源为村镇名人库存、俘虏转化、特殊任务或剧情；刷新受文化、关系、治安、人口、战乱与冷却影响。NPC 也从同类可解释资源渠道获取兵源。

`Party` 持有 leader、成员角色、`Roster`、`PrisonerRoster`、库存/账本引用、位置、目标、士气、组织度、载重。`Army` 聚合多个 Party ID，记录统帅、集合点、凝聚力、命令与成员契约，不复制底层兵力。守军、民兵、商队、村民、强盗等可复用编制容器；民兵和驻军的生成/工资规则各自独立。

```text
RosterEntry = { troop_def_id, healthy_count, wounded_count, xp_buckets[] }
HeroRosterEntry = { hero_id, status }
PartyCapacity = base + clan_bonus + stewardship + leadership + policies - penalties
```

经验按可分配数量处理，升级一个兵不得消耗另一个兵未达到的经验；可采用训练级别桶而非逐人永久记录。任何死亡、受伤、俘虏或升级必须从来源状态扣减、向目标状态增加一次。参战预留从 roster 中划分但不重复扣减总数，结算后释放。军队离散库存由账本事务统一转移。

### 6.2 后勤与士气

每日粮耗按兵力、动物/俘虏及环境规则；从粮类库存按可配置分配规则扣减，不允许负库存。食物多样性、近期战绩、缺粮、拖欠工资、部队组成和统帅能力影响士气；低士气造成逃兵风险，负债影响招募和维持。伤兵恢复消耗时间和资源。队伍载重计算商品、装备、马匹、俘虏与运输能力；驮畜过多也可造成畜群惩罚。军团成员共享补给采用显式转移记录，凝聚力随时间与饥饿、损失衰减，允许补充影响力、分兵、解散、拒绝命令。

### 6.3 玩家管理界面

支持拖拽排序、批量招募/升级/放逐、转移至驻军、俘虏赎回/招降、选择编队角色、预览战斗力与成本、按类筛选、锁定物品、角色分配、创建家族队伍和允许/禁止劫掠、入军团、补驻军等行为。交易前预览最终金钱、兵力、工资、载重；取消不改状态。

### 6.4 验收

`ARM-01` 兵种树、招募、训练、升级、驻军转移；`ARM-02` 后勤、士气、工资与逃兵；`ARM-03` 俘虏、赎回、逃脱和转化；`ARM-04` 军团集结、指挥、凝聚力、解散和成员 AI；`ARM-05` 兵力/经验/货物/金钱守恒，参战前后无复制。

## 07. 经济、贸易、工坊与制造系统

### 7.1 经济闭环与账本

```mermaid
flowchart LR
    V[村庄: 原材料] --> T[运输/商队]
    T --> M[城镇市场]
    M --> W[工坊: 加工]
    W --> M
    M --> H[居民/军队/领主消费]
    H --> X[税收/工资/订单]
    X --> V
    X --> W
    S[战争/治安/天气] --> V
    S --> T
    S --> M
```

物品有稳定 ID、类别、基础价值、质量、重量、堆叠规则、文化、使用条件与资源引用。分类包含食品、牲畜、材料、奢侈品、武器、防具、坐骑、工具等。市场持有库存与可交易资金，村庄产出按周期、季节、繁荣与损失影响。所有增减必须标记为合法来源/去向：生产、消费、磨损、税收、工资、交易、战利品、初始注入、配置补贴。资金账户有交易流水与来源/去向，游戏可以有显式货币产生和回收机制，但不能无原因生成金钱。

### 7.2 报价与市场

以库存覆盖天数、需求、运输成本、繁荣、稀缺性、关系与贸易技能计算中间价。建议初始规则：

```text
coverage = (stock + smoothing) / (daily_demand + smoothing)
mid = clamp(base_price * (target_days / max(coverage, epsilon))^elasticity
            * regional_factor * scarcity_factor, lower, upper)
buy_price  = ceil(mid * (1 + spread_buy + tax + penalties - discounts))
sell_price = floor(mid * (1 - spread_sell - tax - penalties + discounts))
```

所有金额使用最小货币单位整数；分项价格四舍五入策略一致，限制不合理价差；交易量逐批影响价格，报价包含版本、数量、市场库存与双方支付能力，有效期到市场变更。提交时重算或拒绝过期报价；UI 显示改变的价格而非默默扣款。跨城套利允许真实贸易收益，但考虑运输、时间、风险与手续费。商队按预计净利润、货物需求、危险和行程选择路线，受真实库存资金约束；破产/被劫后按保险、赎回、重建策略处理。

### 7.3 工坊与锻造

工坊配方 `inputs → outputs`，拥有资本、原材料库存、产能、工人/维护成本、市场采购和销售策略，可买卖、改型、停产、指定仓储策略。生产须原料充足，成品进入市场或仓库；需求不足时减产，现金流不足时预警，不能无限累积隐藏货物。领地归属变化对营业权和风险生效。

锻造支持熔炼、精炼、锻造、自定义武器部件组合、品质、体力、解锁与订单。部件定义武器类别、几何连接点、重量、长度、伤害类型、基础耐久等；组合后的数值来自平衡公式而非按视觉模型随意生成，合法组合有白名单、长度质量约束及预览。制造事务验证材料、体力、配方、能力、资金与任务订单，成功一次扣除资源并产出唯一物品定义/实例；动态生成物品须可存档、可复制到战场并可网络校验。卖出/熔炼收益经过测试防循环套利。

### 7.4 验收

`ECO-01` 生产—运输—消费完整闭环；`ECO-02` 围城/劫掠造成供应短缺及恢复；`ECO-03` 报价、取消、并发变更、库存与资金一致；`ECO-04` 商队与工坊在不同市场下有利润及破产风险；`ECO-05` 锻造、熔炼、订单、部件约束、成长；`ECO-06` 多年无玩家仿真经济非无限膨胀或普遍崩溃，满足第22章指标。

## 08. 领地、城镇、村庄与治理

### 8.1 领地模型

城镇拥有市场、工坊、酒馆、竞技场、监狱、名人、驻军、民兵、粮仓、建筑及行政数据；城堡偏军事、防御和驻军补给；村庄承担生产、征募、村民队伍与劫掠恢复。地点的控制者（王国/家族）、总督、文化、领地关系、初始模型与当前状态分开存储。场景中访问的商人/领主必须根据世界状态生成或隐藏；不可通过固定 NPC 节点长期保有已死亡的领主。

### 8.2 发展与建设

| 变量 | 主要输入 | 主要输出 |
|---|---|---|
| 繁荣 | 贸易流、粮食、治安、战争、建筑 | 税收、需求、招募能力 |
| 粮食 | 村庄产出、市场、库存、驻军消耗、围城 | 饥荒、驻军健康、繁荣 |
| 忠诚 | 文化差异、总督、政策、治安、饥荒 | 税收/建设效率、叛乱风险 |
| 治安 | 驻军、名人关系、犯罪、盗匪、领地事件 | 招募、商路安全、忠诚 |
| 民兵 | 人口、忠诚、繁荣、训练 | 防御兵力、领地安全 |
| 城防 | 建筑等级、城门/城墙损坏、修缮 | 攻城时可用工事与导航变体 |

变量使用日变化和上下限，明确来源；避免负反馈无限放大。建筑采用配置化的前置关系、等级、成本、工期、维护与效果，建设队列可暂停、调整、取消。政治归属转移时按配置保留建筑与库存、重新任命总督，更新税收归属、外交、任务可达性和地图 UI。

领地治理包含税收、驻军工资上限、自动招募/训练、粮食与建筑资源、总督技能、日常项目（修缮、粮产、治安、忠诚等）。低忠诚与弱守军可能触发叛乱，创建合法新势力或暂时控制者；不能直接让领地无主或复制驻军。围城中断贸易、消耗粮食、损坏工事；占领后有处置/恢复规则、民众关系、战俘和战利品。村庄劫掠经过可中断进度、损失、恢复冷却，禁止重复即时获取同批物品。

### 8.3 城镇生活与非法活动

场景菜单和 3D 访问共享用例，玩家可找商人、名人、酒馆同伴、赎金中介、竞技负责人、工匠、领主、总督。支持守卫检查、潜入敌城、犯罪声望、街区帮派冲突、控制街巷、走私/监狱越狱、酒馆小游戏等世界互动；具体规则、内容与美术采用原创实现。进入限制根据身份、外交、犯罪、任务状态和装备类型动态判断；捕获/失败处理回归地图状态。

### 8.4 验收

`SET-01` 治理、建设、领地收益和驻军维护可持续运行；`SET-02` 占领/叛乱/易主与家族、财政、外交保持一致；`SET-03` 围城、劫掠、饥荒与恢复产生可观察的系统变化；`SET-04` 所有主要城镇访问与互动由同一世界状态生成，支持合法和非法路径。

## 09. 王国政治、外交、战争与战略 AI

### 9.1 政治实体与权力

`Kingdom` 持有君主、成员家族、国策、财政引用、政治决议、军团、外交关系；`Clan` 是成员与经济单元；`Settlement.owner_clan_id` 决定封地归属，王国关系从家族成员资格推导，叛乱/独立势力例外显式建模。允许独立家族、佣兵合同、封臣关系、君主继承、投奔、退国、建国、授封与收回封地。雇佣、效忠、退约、叛离会改变收入、战争关系、影响力及名望，不允许同一队伍同时归属冲突阵营。

决议流程：合法提案 → 候选方案冻结 → 投票窗口 → 各有权家族按规则投入影响力 → 统计 → 君主依法确认或否决 → 统一事务提交。决议处理国策、宣战/议和、封地归属、统帅/君主人选等。政策使用可配置效果、叠加顺序、冲突条件与适用范围；UI 展示候选方案、票数、影响力成本和影响。所有投票命令具备权限与期限校验，AI 和玩家使用同一接口。

### 9.2 外交与战争

国家间关系使用唯一无序对（A,B）维护战争/和平状态；和约、贡金、期限、赔款、休战、停战条件独立。宣战触发敌对关系与战役目标，而非直接启动战斗。议和取消非法敌对行动、释放或按合同处理俘虏/军团，并刷新市场通行。人物/家族私仇、犯罪、处决、好感不等价于国家宣战；仇怨与和解有明确作用域，避免无限报复。支持谈判交易（土地/金钱/婚姻/赎金等）与政治条件验证；任何协议在接受前验证双方资产和授权。

战争统计：敌对兵力、损失、囚禁领主、领地变动、劫掠、财政、补给、战略目标。战败导致资源减少，不给失败方无上限补兵；国家灭亡与重组规则需处理幸存家族、队伍、领地、未结算协议、任务引用。国家可以通过合理的重建/投奔行为复起，但不强制永久存活。

### 9.3 战略 AI 设计

| 层级 | 输入 | 目标与输出 |
|---|---|---|
| 王国规划 | 边境、力量对比、政治意愿、财富、现有战争 | 战略目标、议和/宣战建议、增援优先级 |
| 家族规划 | 封地、资金、关系、名望、人物角色 | 招募、经营、投票、婚配、投奔、组建军队 |
| 军团规划 | 凝聚力、补给、敌情、友军、地图通行 | 集合、围城、解围、接战、撤退、解散 |
| 队伍规划 | 当前兵力、目标、情报、食物、工资、性格 | 巡逻、追击、逃离、贸易、回城、招兵、交战 |

战略 AI 采用候选生成 + Utility AI（效用评分）+ 任务状态机；复杂计划使用有限层次任务网络（HTN）分解，不依赖实时大模型。候选先做硬约束过滤，再综合收益、成功概率、危险、成本、紧迫性与性格。目标锁定时间、滞回、失败冷却和随机扰动避免高频反复切换。商队、盗匪、村民、领主共享移动和资源用例但采用不同策略配置。全局调度器分片运行，不为所有队伍每帧执行昂贵路径查询。

```text
candidate_score = priority * expected_value * success_probability
                  - travel_cost - risk * risk_aversion - resource_cost
                  + urgency + personality_bias
if new_score < current_score + switch_margin: retain_current_plan
```

例：军团欲攻城，先评估附近可用部队、围城所需时长、粮食、城防、敌方援军与城池价值；执行集结、行军、围城；若粮食不足或敌援优势改变则换为补给/撤退。AI 命令生成只读快照，提交时重新校验资源和世界版本。不能凭不可见敌军的位置预判路径。

### 9.4 自动战斗

不加载实时 Mission 的遭遇采用分段交锋模型，按兵种角色、数量、装备等级、地形、兵力比、士气、技能与战术修正有效战力。每回合按角色克制和伤亡概率扣减兵力，保持英雄存活/被俘规则；超出回合预算则处理撤退/决胜。相同输入与随机种子可复现纯逻辑结果，输出同一 `EncounterResult` 语义。玩家选择派兵自动解决时使用相同基础模型，可配置风险与指挥技能；通过离线批量实时战斗统计校准其胜率和伤亡分布，不追求每局精确等价。不得自动结算已租用为玩家实时战场的兵力。

### 9.5 验收

`POL-01` 家族身份、佣兵/封臣、建国、退国和继任；`POL-02` 决议投票、政策与影响力账本；`POL-03` 宣战/议和、贡金、谈判与仇怨；`POL-04` 领地与王国兴亡、政治引用完整性；`SAI-01` 资源有限下的王国/家族/军团/队伍行为；`SAI-02` 自动战斗复现与伤亡守恒；`SAI-03` AI 长期仿真有合理战争、和平、复苏和经济轨迹。

## 10. 任务场景与实时战斗运行时

### 10.1 通用 Mission 容器

Mission 是一段具备独立生命周期的局部场景模拟。它包含场景地图、角色实体、阵营、编队、规则、目标、控制器、生成调度、环境状态和结果收集。支持野战、攻城、突袭、藏身处、竞技场、城镇访问、对话/剧情、多人模式。非战斗 Mission 可禁用战斗/编队系统而保留角色移动和交互。各玩法通过组合行为和规则实现，不通过复制整个战场场景来开发新玩法。

```mermaid
flowchart TD
    E[EncounterSpec 或 Custom/MultiplayerSpec] --> L[加载 SceneDef 与资源]
    L --> V[校验出生/导航/目标/规则]
    V --> M[MissionContext: Team/Agent/Formation]
    M --> D[部署/准备]
    D --> T[实时固定步长模拟]
    T --> O[目标/波次/伤亡/撤退]
    O --> T
    O --> R[MissionResult]
    R --> C[结果路由: 战役/自定义/多人]
```

每个 Mission 拥有独立的事件域、随机流、资源租约和 EntityHandle 命名空间；禁止旧 Mission 的异步回调写入新任务。场景结束流程为停止输入 → 固定 tick 屏障 → 生成结果 → 提交/展示 → 释放导航与物理、实体和资源 → 回到会话。场景定义包含出生区、导航区域、目标点、撤退边界、相机限制、交互点及对应验证器。

### 10.2 进入与离开战场：跨域事务

战役 `Encounter` 状态机：`Created → Negotiating → Reserved → MissionRunning | AutoResolving → ResultReady → Committed | Cancelled`。开始战斗前冻结参战双方、合法行动、兵力来源、英雄装备快照和场景选择；使用 roster 预留记录（不是复制兵力），锁定相关实体的变更。用户退出/加载失败按策略解除预留或读取战前检查点。战役关键时间在玩家战斗期间冻结；战斗时长换算和战后世界时间推进由统一规则决定。

```mermaid
sequenceDiagram
    participant C as Campaign/Encounter
    participant S as GameSession
    participant M as MissionRuntime
    participant P as Persistence
    C->>C: validate + reserve rosters
    C->>P: durable pre-battle checkpoint
    C->>S: EncounterSpec(encounter_id, revision)
    S->>M: prepare(spec)
    M->>M: deploy, simulate, finalize
    M->>S: MissionResult(result_id, source outcomes)
    S->>C: CommitEncounterResult
    C->>C: validate reservation + result invariants
    C->>P: atomic commit state and applied_result_id
    C-->>S: settlement receipt
    S->>M: dispose
```

结果以来源 PartyId、TroopDefId、HeroId、初始预留槽位及唯一战场实体句柄追踪。结束时每个参与槽位最终分到存活/受伤/阵亡/被俘/撤离/未入场之一（撤离是否受伤由独立字段记录）。未进入战场的预备队仍必须有明确归属；不能把未生成兵力当作阵亡。俘虏只在结算时依据胜负、逃脱、容量规则从源 roster 转到目标 prisoner roster；英雄不能既在家族队伍又被俘。经验、战利品、旗帜、名望、领地占领和军队关系一并核算；重试 `result_id` 必须幂等。断电恢复要么读提交前快照，要么读提交后快照，绝不重复发放。

### 10.3 战斗部署与增援

`BattleRule` 管理开局时间、允许的阵营、伤亡/士气、目标、撤离、玩家击倒后指挥模式、战斗结束与胜负。开战前可按队长、兵种、装备、数量和出生区域分配编队、指定初始阵型；部署位置必须可达且不能跨越对方出生线。战场总兵力可以大于同屏上限，SpawnDirector 根据参战配额、剩余兵力、增援规则、当前单位数、预备队与安全生成点分批进入。避免增援直接生成在敌人或玩家视野前方无合理解释的位置；可用边界/集结点、波次冷却和路线。

英雄被击倒时可以按规则继续观察、委派指挥、撤离或自动结算；其身份和伤情独立于控制器是否存在。战斗中切换镜头或接管其他士兵必须由规则授权，不直接变更 HeroId。多人重生同样由规则管理，而非复活持久战役角色。

### 10.4 战斗 tick 与一致性

建议 60 Hz 固定战场模拟步长（低配置可用经校准的 30 Hz），渲染插值解耦。具体频率冻结前需实测。每个 tick 依次：

1. 收集输入和命令，验证控制权、序号、动作状态；同步动态障碍/感知快照。
2. 到期战术/编队任务生成命令，个体 AI 根据快照生成意图，玩家使用同类意图。
3. 移动系统更新期望速度、局部避障及物理/运动积分，取得可靠碰撞查询数据。
4. 动作时间轴推进、武器与弹体扫掠、候选命中生成；收集并按稳定规则排序。
5. 格挡/伤害/击倒/状态转换、士气和成员数更新；同 tick 的相互命中采用明确的同时性规则（以伤害阶段开始快照决定有效攻击）。
6. 更新目标、撤退、波次与结束条件；提交权威状态，生成视觉事件/读快照；清理延迟销毁实体。

如果战斗已经进入结束态，仅执行清理/结算所需逻辑，不再接受改变结果的输入。工作线程只处理快照上的纯计算；提交在权威阶段完成。状态版本/tick 标记随结果传播，过期 AI 工作丢弃或重新计算。

### 10.5 验收

`BAT-01` 野战完整部署—战斗—胜负—结果闭环；`BAT-02` 大军增援、英雄击倒、撤离、俘虏、未上场兵力；`BAT-03` 跨域提交幂等、存档中断和载入失败恢复；`BAT-04` 自定义战斗不改战役；`BAT-05` 不同 Mission 规则可组合且生命周期无泄漏。

## 11. 动作、移动、装备与战斗系统

### 11.1 Agent 组成

一个战场 Agent 代表实际可控制单位，逻辑状态包括 `AgentId/TeamId/FormationId/SourceSlot`、位姿/速度、生命/状态、装备快照、动作、移动模式、感知、技能与士气。骑兵的骑手和坐骑分开建模（各自生命、碰撞及状态），由 MountLink 表示乘骑关系；马匹不是简单的角色移动倍率。场景中的视觉节点通过句柄关联权威状态，而非将节点路径作为身份。Agent 不保存对 Campaign 对象的引用。

建议逻辑组件：Identity、Transform、Kinematics、Health、Equipment、ActionState、Perception、AIState、FormationMember、MountLink、CombatStats。常用数字组件采用连续数组存储；低频独立属性采用普通对象。组件数据的生命周期受 Mission 管理，实体句柄带 generation，避免对象池复用导致旧引用误伤新实体。

### 11.2 玩家输入、动作与控制权

支持第一/第三人称视角、方向移动、步行/跑动、冲刺或步态、跳跃（场景允许时）、蹲伏、攻击/防御方向、弓弩瞄准与装填、投掷、切换武器、持盾、骑乘/下马、交互、战场命令。输入系统把设备输入转换为 `MoveIntent`、`LookIntent`、`AttackIntent`、`BlockIntent`、`EquipIntent` 等规范意图。相机可以影响瞄准但不改变已提交的攻击权威规则；手柄/鼠标灵敏度、反转、方向攻击映射和无障碍选项在本地配置。

动作状态机建议：

```mermaid
stateDiagram-v2
    [*] --> Ready
    Ready --> Windup: attack direction selected
    Windup --> Hold: charge ready
    Hold --> Active: release
    Windup --> Ready: permitted cancel
    Active --> Recovery
    Recovery --> Ready
    Ready --> Guard
    Guard --> Ready
    Guard --> Stagger: guard break
    Active --> Stagger: interrupt
    Ready --> Stagger: hit
    Stagger --> Ready
    Stagger --> Downed: hp exhausted
    Active --> Downed: lethal hit
    Downed --> [*]
```

图示省略格挡反击、踢击、武器切换、骑乘与装填等正交状态；实际实现使用动作 FSM + 移动/骑乘 FSM + 状态标签与取消表，避免组合状态爆炸。攻击数据规定蓄力、有效命中窗、恢复、方向、体力（如规则启用）、连击/取消、攻击碰撞轨迹及硬直。动作层输出根运动请求与动画表现事件；视觉动画必须与权威攻击窗口同步，不允许仅依赖动画播放结束判断命中。

### 11.3 近战与远程

- 近战包含左右挥砍、上劈、刺击，武器类型可限制动作集合；命中依照武器扫掠体/轨迹和目标身体区域检测，并处理障碍、盾牌、武器格挡、友军碰撞和多人模式友伤规则。每次攻击有唯一 AttackId 与已命中集合，防止同一帧/多个骨骼重复伤害；可配置多目标挥砍能力及最大目标数。
- 防御按武器方向格挡、盾牌覆盖、角度、距离、时机、耐久/破防规则判定。格挡成功与否不依赖客户端视觉推断；盾牌破坏后更新装备并触发动画。
- 远程武器具有装填、蓄力、散布、弹药、重力、初速度、弹体碰撞和距离衰减；服务端/单人权威生成弹体。高速弹体采用分段/连续扫掠，禁止仅靠离散帧位置判断；弹体数量受预算限制但不能无故丢失有效伤害。
- 攻击结果可产生击倒、硬直、盾牌破坏、马匹受惊、武器受阻、命中音效/特效与士气影响。表现事件记录位置、材质、攻击 ID、伤害结果与是否可见，客户端仅消费已确认事件或回滚预测表现。

### 11.4 伤害与装备规则（独立数值方案）

武器定义包含伤害类型（砍/刺/钝）、质量、长度、速度、握持方式、攻击模板、有效轨迹、使用要求；护甲按身体区域、材质与类型设防护。计算分阶段保留 `DamageBreakdown`，供调试和 UI：

```text
raw = weapon_base * action_modifier * charge_factor
      * speed_factor(relative_impact_speed) * skill_factor
zone_damage = raw * hit_zone_multiplier
mitigation = armor / (armor + penetration_scale[type])
actual = max(0, round(zone_damage * (1 - mitigation) * difficulty_multiplier))
```

正式实现将格挡/盾牌/免疫判定放在计算之前；相对速度倍率限幅，区分伤害类型与穿透；护甲伤害、冲击硬直与骑兵冲撞使用独立模型，不无限叠加。暴击/命中随机必须可测试，且动作成功的因果反馈明确。伤亡分类与战役医术相关但由结算规则确定，不由动画状态随意决定。

### 11.5 骑乘、移动与地形

骑乘状态包含上马/下马、转向、加减速、步态、碰撞、骑手攻击方向、骑枪冲刺/架枪与落马；骑手可受独立攻击，马匹失能时解除挂接并落马。马匹采用速度依赖转向与制动、体积与冲撞限制；路径代价考虑转向半径与地形坡度，狭窄城墙/楼梯禁入骑兵。落马/尸体不应造成导航永久阻塞；战场模式决定可重新拾取坐骑/装备。

步兵移动以期望速度与方向为输入，考虑地形、坡度、碰撞体、近距离拥挤和战斗状态。碰撞/位姿求解优先采用受控运动模型；不为所有普通士兵持续启用完整刚体 ragdoll。尸体特效可预算裁剪但已判定伤亡不可变。统一坐标、单位（战场米、秒、角度/弧度约定）与动作数据规范。

### 11.6 验收

`COM-01` 四向近战与防御、蓄力/取消/硬直/武器碰撞；`COM-02` 弓弩与投掷、弹药、遮挡、弹道/高速命中；`COM-03` 护甲/身体区域/盾牌/装备切换、伤害可解释；`COM-04` 骑乘、冲撞、马匹受伤和落马；`COM-05` 玩家与 AI 使用一致动作接口，固定 tick 与渲染帧率解耦；`COM-06` 多人预测不能造成重复伤害或越权动作。

## 12. 战场 AI、编队、指挥与导航

### 12.1 层级与控制权

参考游戏公开开发日志描述了个体、编队、战术三层 AI；本项目沿用这一抽象思想，具体算法独立设计。战略 AI 在战役域，战场 AI 仅处理当前 Mission。

```mermaid
flowchart TD
    P[玩家指挥输入] --> O[OrderAuthority / OrderRouter]
    T[战术 AI: 全军计划] --> O
    O --> F[编队命令与授权]
    F --> A[编队 AI: 目标/阵型/行为]
    A --> S[槽位分配与局部目标]
    S --> I[个体 AI: 感知/决策/动作意图]
    I --> M[移动与战斗执行系统]
    M --> W[战场权威状态]
    W --> Q[可见战场快照/统计]
    Q --> T
    Q --> A
    Q --> I
```

玩家直接控制一个角色，同时可指挥有权限的编队。每支编队的控制权明确：玩家、AI 统帅、委派队长、多人队长等。指挥命令有发起人、编队集合、序号、类型、目标、参数、完成条件；新命令替换/排队规则由类型定义。玩家命令优先于委派 AI；玩家明确委派后 AI 获得有限权限。AI 不得在玩家不知情情况下任意覆盖命令。遭遇危险、道路不可达、编队溃散等安全/失效规则允许单位局部自主调整，记录原因。

### 12.2 指挥功能

| 命令类别 | 操作与行为 |
|---|---|
| 位置 | 到指定位置、跟随、面向方向/敌人、保持、推进、撤退、冲锋指定编队 |
| 阵型 | 横队、盾墙、散阵、方阵、圆阵、楔形、纵队等 |
| 行动约束 | 开火/停火、使用远程武器、骑乘/下马、保持距离、自由攻击 |
| 编队组织 | 选择全军/多选/编号、分配兵种、分组/合并、委派指挥、队长任命 |
| 攻城 | 破门、登梯、操作器械、守城墙、通过缺口、争夺目标 |

命令系统将键位/UI、AI 决策与网络消息统一到 `FormationOrder`，UI 提供部署预览、目标标记、选择反馈和当前命令，失败/不可达须可理解。具体命令类型由规则注册，非战斗场景禁用。一次命令不会直接触发全部士兵执行相同动画，而是修改编队目标与行为约束。

### 12.3 战术层

每支 Team 建立 `BattlefieldSnapshot`：已知敌方编队、己方有效兵力/角色、敌我接触线、可达地形、制高点、防御工事、伤亡、士气、弓箭弹药、目标进度、增援。战术库可组合防守高地、步兵压迫、弓兵掩护、骑兵侧翼、骑射骚扰、预备队、围城分路等原创游戏行为。评分考虑可达性、兵力构成、地形、有效射线、敌我强度、风险、指挥官特质。战术由阶段和触发器组成；每个编队分配 `FormationTask`（目标、职责、约束、优先级、完成条件、超时）。执行失败进入回退计划，而非每次重新生成完整计划。

战术更新建议 0.5–2 Hz 或关键事件触发，更新预算可分帧；阵型或目标高频变化不应诱发全军每帧重新选战术。

### 12.4 编队层

编队是独立决策单元，维护成员列表、阵型、中心/朝向、槽位、命令、敌情、角色/能力聚合与士气。根据战术任务选择保持、移动、射击、推进、冲锋、撤退、重组等状态。阵型生成器按成员数量、间距、角色尺寸和地形生成局部槽位；将槽位投影到可达导航区域并计算压缩/分列策略。分配采用近邻、角色/行列约束与稳定匹配，人数多时避免每 tick O(N³) 的全局匹配；损失/编队变化后局部重分配并防抖。复杂地形（门洞、楼梯、城墙）自动切换可通行队形，出瓶颈后恢复。

编队移动由中心路径 + 槽位跟随 + 局部避障构成；不能只让所有个体独立 A* 到同一点。槽位偏差、前进方向和队友密度驱动速度，紧急脱离时允许暂时打破槽位。近战接敌后局部寻找可攻击位置，结束交锋后再重组。编队 AI 建议 2–5 Hz，跟随与槽位纠正可高频执行。

### 12.5 个体 AI

每个 Agent 使用轻量分层状态机 + 效用选择（或小型行为树）。高层状态：执行命令、移动至槽位、交战、受击恢复、寻找坐骑、操作器械、溃逃、失能。感知通过空间索引查询有限数量近邻，检查阵营、视线、距离与威胁；目标评分考虑可达距离、威胁、对手类型、占位/围攻数量、与编队命令冲突程度。目标锁定与更换冷却避免抖动，少量紧急反应（格挡、受击、躲避碰撞）不等待完整行为更新。

```text
perception = SenseNearby(snapshot, agent_id, radius, max_candidates)
if incapacitated: return NoIntent
if routing: return MoveToSafeExit()
if immediate_threat and can_react: return GuardOrEvade()
if assigned_to_engine: return OperateAssignedDevice()
if order_requires_formation and slot_error > threshold: return MoveToSlot()
if target_valid and attack_in_range: return SelectAttackOrGuard()
if order_allows_engagement: return ApproachOrFire(target)
return HoldOrFollow()
```

个体决策建议 5–20 Hz，临近玩家/敌人优先；移动与动作执行保持固定模拟频率。难度影响反应延迟、判断误差、格挡能力与协调性，而非所有敌人同时精准反应。人群 AI 的性能优化不得让远方真实战斗完全停止；按距离和重要性使用分级更新与简化感知。

### 12.6 导航与人群

战略导航与战术导航使用不同坐标空间和数据。战场 NavMesh 为步兵、骑兵、器械建立可达性，支持门、梯、坡道、桥、墙缺口、登船接口等动态 Link。路径服务接受批量带优先级请求，支持缓存/版本失效、不可达结果、限时查询；编队共享走廊，个体只在必要时局部规划。局部避障采用空间哈希/网格与速度障碍或其他邻域算法，结合站位、通行方向、碰撞软约束，防止所有单位聚集后完全冻结。

动态障碍变化只使影响区域的路径失效；门/缺口变更使用预定义导航连接或局部重建，不能每次破坏全图重新烘焙。设置拥堵检测、让行、回退、重新分配路径和超时退出；不得通过传送普通单位隐藏系统错误。导航与物理相位同步需由引擎适配层处理。

### 12.7 士气与撤退

战场士气不同于长期队伍士气；初始值来自战役队伍、将领能力和场景。伤亡、包围、近邻溃散、将领击倒、敌人撤退、己方增援等事件改变个体与编队士气，传播限频且有衰减。达到阈值进入溃逃状态并朝合法撤离区移动，可在条件允许时重新集结；撤退、逃散、俘虏、无路可退的结果规则区分。胜负不仅依据生命归零，也依据目标、撤退与剩余可战力量。

### 12.8 验收

`BAI-01` 三层战场 AI 与统一命令接口、委派和控制权；`BAI-02` 七类阵型、动态槽位、伤亡重组与狭窄通路；`BAI-03` 步兵、远程、骑兵、骑射的角色行为和反应；`BAI-04` 战术目标、地形利用、退却和改计划；`BAI-05` 士气与目标信息遵守可见性，玩家命令反馈清晰；`NAV-01` 动态门/梯/缺口、路径预算与拥堵恢复；`BAI-06` 大规模压力下达到第19、22章指标。

## 13. 攻城、遭遇与其他任务场景

### 13.1 攻城分两阶段

战略阶段：围城方选择目标，建立营地，阻断交通，调度建造器械与补给，守军消耗粮食并修复城防，双方远程攻城设施交锋，援军可解围。`SiegeState` 记录目标、参与方、建设进度、器械、城防破坏、预留资源、围城开始时间与可用补给。可选择继续围困、谈判、强攻、派兵、撤围、守军出击或突袭器械。围城是持久事件，不等于实时战场；战场加载使用围城快照。

实时阶段：装载城墙、城门、塔楼、梯子、攻城塔、冲车、投射器械和损坏变体；编队根据攻/守目标选择入口、操作器械、掩护、攀登、驻守、反击。器械状态包含装配、移动、就位、装填、发射、损坏、失效与乘员槽；器械有独立实体和碰撞。门与城墙使用预设可破坏组件/阶段模型，破坏提交触发导航 Link 开关和目标变化。必须有攻城塔/梯路可达性验证、城门阻塞处理、落差安全点、守军替补和拥堵回退机制。

目标规则支持突破城防、占领关键目标、击溃/撤退、守城计时或多阶段要塞战；不将单一击杀数当成所有模式的胜利条件。攻城结束把器械损毁、城防损坏、伤亡和领地控制事务回写；失败攻城可能返回持续围城，而非强制结束整场战争。

### 13.2 其他任务类型与规则复用

| 类型 | 主要玩法 | 特殊规则/数据 |
|---|---|---|
| 野战 | 双方军队、地形、编队、增援、士气 | 战斗地形匹配战略位置、撤离边界 |
| 村庄/沿途遭遇 | 袭击、护送、救援、追击、反击 | 保护对象、非战斗人员、可中断目标 |
| 藏身处 | 小队渗入、逐区交战、首领/撤离 | 人数上限、出生区与任务步骤 |
| 竞技场/锦标赛 | 决斗、分队、多轮淘汰、赌注与奖励 | 临时装备、非致命规则、奖金事务 |
| 城镇/村庄访问 | 自由走动、对话、商店、招募、场景互动 | 便装、身份权限、NPC 动态排班 |
| 监狱/潜入/街区 | 小规模战斗、逃离、救人、非法活动 | 守卫反应、犯罪、被捕与回退 |
| 训练/主线任务 | 教程、特殊目标、阶段剧情、对话 | 独立阶段和检查点，失败可恢复 |

模式使用 `MissionDefinition` 声明需要的组件：Spawn、Combat、Interaction、Formation、Objective、Round、Reward、Weather 等。Rule 实现 `on_start / on_tick / on_event / check_outcome / build_result`；扩展目标组件可独立加入，不改核心战斗器。竞技场中的临时装备不能流入长期库存；任务奖励只由战役结算发放。对话/互动触发通过授权 Command，场景脚本不可直接写家族/市场。

### 13.3 验收

`SGE-01` 围城营地、器械建造、封锁、粮耗、破坏及解围；`SGE-02` 真实攻守、梯/塔/门/器械使用、动态导航；`SGE-03` 守军出击、撤围、占领与回写；`MIS-01` 野战、村庄、藏身处、竞技、访问、潜入与剧情场景类型完整；`MIS-02` 任一场景规则独立切换，奖励、装备与兵力不串域；`MIS-03` 场景编译器拒绝缺出生点、失效链接或不可达目标的内容。

## 14. 任务、剧情、对话与动态事件

### 14.1 数据驱动的任务状态机

`QuestDefinition` 包含发布者筛选、前置条件、阶段图、目标、期限、奖励/惩罚、失效条件、可重复策略、文本键与引用资源。`QuestInstance` 记录实例 ID、定义版本、参与实体 ID、当前阶段、计数器、期限、随机选择和状态。阶段支持等待事件、计数、交付、保护目标、到达地点、完成 Mission、选择对话分支；禁止任意脚本直接改底层存档。任务状态：Available → Accepted → Active → Completed | Failed | Expired | Cancelled，奖励领取状态独立并具备幂等 ID。

事件匹配使用已提交的领域事件（例如 `PartyDefeated`、`GoodsDelivered`、`SettlementOwnerChanged`）；任务实例只消费一次符合条件的事件，重载存档不能重复奖励。人物死亡、被俘、领地易主、阵营消亡或目标已完成时有明确替代路径/失败规则。任务生成依据真实世界矛盾与可达资源，避免请求不存在的物品或不可访问的地点。剧情强制对象若需保护，规则明确标识；一般沙盒实体不因任务隐式永生。

### 14.2 剧情战役

采用 StoryDirector 管理原创故事阶段：角色与世界介绍、教程、家族危机、势力选择、战争/政治主线、结果与沙盒继续。阶段与目标定义可配置，不依赖固定历史人物、原作台词或地图。教程覆盖移动、格挡、骑乘、招募、交易、指挥和地图操作；允许跳过已掌握内容。主线有分支和可重试关键任务；超时、失败或关键角色消失按设计转为替代剧情或开放沙盒，不破坏长期存档。沙盒模式不注册强制主线，但与剧情模式共享世界和任务引擎。

### 14.3 对话和动态事件

对话图由节点、说话者、文本本地化键、显示条件、选择、用例命令、下一节点构成。支持关系/技能说服、交易谈判、婚姻、招募、投诚、俘虏赎回、任务与传闻。对话开场读取实时状态，执行选择时再校验；异步状态变化或角色不在场时给出退出/替代分支。说服检定依据可见条件和随机流，避免重复读档外的无限刷选项；失败可有冷却。

动态事件引擎依靠日结、领地、关系、战争与人物变化发出事件机会，按地区、冷却、权重、可达性及并发任务容量生成任务。内容种类包括护送、商队、训练、供货、打击盗匪、调解争端、领地支援、赎俘、征兵、家族事件等。消息、日志和百科保存结果摘要，玩家可追溯原因。

### 14.4 验收

`QST-01` 数据定义支持多阶段、分支、期限、失败及重复；`QST-02` 关键实体失效有替代处理，无孤儿任务或重复奖励；`QST-03` 剧情开局、完整主线和沙盒继续；`QST-04` 对话/说服/交易与任务使用统一命令；`QST-05` 动态任务生成可达、可完成且长期运行不无限增长。

UI 使用 ReadModel + Command，而非绑定可变领域实体。面板订阅批量更新，按需刷新；列表虚拟化、搜索筛选、快捷键、控制器导航。所有关键变更提供预览和失败原因，物品/技能/经济公式可显示分项解释。战略提示与百科尊重玩家可见信息；战场地图和观战权限由规则决定。

### 15.2 表现架构

动画分层：基础移动、方向攻击、上身瞄准/格挡、骑乘、受击、死亡/布娃娃、交互，使用混合、动作标记与必要的 IK。权威命中时间和动作长度由数据控制，动画标记在构建时验证；视觉蒙皮、LOD、插值不可反向决定实际伤害。角色资产按体型/文化/装备骨架规范装配，支持换装及材质变体，遮挡的身体网格裁剪。旗帜、阵营色与轮廓辅助辨识；镜头避免进入几何体，近战和马背视角具有独立限制。

环境采用区域主题、季节/天气、日夜、植被、地形、材质、烘焙光照或动态照明组合。天气视觉与战役/战场规则可有关联，但不能仅凭粒子特效决定真实滑移、视距和弓箭表现。音频通过 Voice/Effects/Music/Ambience/UI 混音总线、优先级、距离衰减、空间声、并发预算管理。战斗语音传递命令/警告，不能被大量远处撞击淹没；音乐按战略、战斗、胜败状态切换。字幕、UI 文本和语音 ID 分离，支持本地化复数、变量与字体回退。

### 15.3 验收

`UX-01` 所有主要玩法可通过键鼠/手柄操作，有错误提示与确认；`UX-02` 战场可读、编队命令与目标清晰；`UX-03` 本地化无硬编码文本、分辨率/字号支持；`VIS-01` 装备骨架与动作一致，命中反馈正确；`AUD-01` 大战场音源预算、混音与命令可辨识；`ACC-01` 可访问性和难度选项均可保存、恢复和测试。

## 16. 多人联机与在线服务

### 16.1 目标与边界

多人是完整本体的一部分，主要交付独立战斗赛局：决斗、小队对抗、团队死亡竞赛、队长（玩家统领 AI 小队）、大型战斗/攻城。单人沙盒采用本地权威；多人使用专用权威服务器，共享 Combat、Mission、Formation、目标规则和数据定义。不承诺多人共同持久化整个战役；若未来加入联机战役，需要额外解决战略时间同步、共同存档和所有权，不混入现有协议。服务器玩家容量与战场 AI 容量分别压测，建议先按 64/128 真人规模设计配置，200+ 为压力/扩展目标，不视为已经达到。

```mermaid
flowchart LR
    P[客户端: 输入/预测/插值] <-->|命令/状态快照| D[专用权威 Mission Server]
    P --> A[认证/大厅/服务器发现]
    A --> K[匹配/房间分配]
    K --> D
    D --> H[赛局结果/日志/健康报告]
    H --> B[账号与赛季数据/处罚服务]
```

后端最小部署边界为账号/会话、服务器目录/大厅、匹配与服务器分配、结果/处罚；可先使用单个后台服务实现逻辑模块，专用战斗服务器独立扩容。玩家身份可由平台 SDK 或自建账号提供，域层仅依赖身份接口。自托管服务器提供配置、管理员权限、地图轮换和日志；官方排名和玩家自建规则分离，避免自托管结果篡改排名。

### 16.2 网络模型

服务器验证玩家令牌、内容协议/模组版本、角色权限、命令序号、输入速率、位置/动作合法性。客户端不直接发送生命、命中、金钱或结果。客户端预测自身移动/部分动作，收到权威快照后重放尚未确认的输入，远端实体使用插值缓冲；必须定义校正阈值和视觉过渡。服务器侧命中补偿基于受限历史快照与明确最大回溯窗，不允许客户端选择任意旧时间；近战、弹体、格挡与盾牌各有一致的补偿政策，压力测试后冻结。物理不要求跨平台锁步。

| 通道 | 数据 | 传输/处理 |
|---|---|---|
| Control | 登录、房间、准备、阵营、装备选择、回合状态 | 可靠、有序、鉴权 |
| Input | 移动、视角、攻击/格挡意图 | 高频序列、可冗余、丢弃过期输入 |
| Orders | 编队命令、委派、选目标 | 可靠、幂等、控制权校验 |
| Snapshot | 实体位姿、动作状态、生命摘要、编队/目标 | 增量、序号、基线确认、兴趣管理 |
| ImportantEvent | 死亡、出生、目标占领、结果、强制校正 | 可靠或重复确认；去重 |
| Cosmetic | 特效、普通音效、非关键表现 | 可丢弃，不影响权威 |

包头含 protocol_version、session_id、sequence、tick、ack/基线、消息类型和长度；限制包体与数组长度。序列回绕、迟到、重复、乱序、丢包均有测试。快照按兴趣区域、角色重要性和场景规则裁剪，观战者只能读取允许的视角。服务器在版本不一致时拒绝进入或引导匹配对应版本，不能让客户端自行执行不可信模组规则。

建议服务器固定模拟 30/60 Hz（按容量压测），快照 10–20 Hz 起步；网络帧率和游戏模拟频率分离。带宽预算示例：150 个相关实体 × 平均 24 B 增量 × 15 次/秒 ≈ 54 KB/s，实际需计入协议、关键事件和峰值；使用量化、变化掩码、实体重要度和增量基线控制流量。玩家容量大时以真实压测评估，不以算术估计替代测试。

### 16.3 匹配、规则与公平性

大厅支持组队、地域/延迟、模式选择、服务器列表、加入中途赛局、地图投票、重连与队伍平衡。赛局规则定义胜负、回合、出生、重生、装备/职业预算、团队配合、友伤、掉线惩罚和观战。队长模式复用 Formation 权限，每玩家对应合法编队；玩家死亡后的单位控制或观战由模式规则决定。攻城支持阶段目标、资源与守军/攻方出生规则，不依赖单人永久数据。

防作弊设计：服务器权威、命令速率和参数校验、输入/动作时序检查、异常移动/瞄准统计、内容哈希、管理员审计、举报和封禁/申诉流程。客户端防作弊能力可外接合规方案；日志最小化个人信息，不把客户端完整文件扫描作为默认。聊天/语音需要静音、屏蔽、举报和管理；身份、令牌及账号数据采用加密传输与访问控制，凭证不写普通日志。结果提交带唯一赛局 ID 及服务器身份，可重试不重复发奖；服务故障应允许私人服务器继续本地模式，官方排名明确不可用。

### 16.4 验收

`NET-01` 专用服务器可无渲染运行、与客户端规则一致；`NET-02` 全部主要模式、匹配/服务器发现、队长与攻城；`NET-03` 延迟/丢包/重连/乱序下状态收敛；`NET-04` 无权客户端无法生成伤害/修改生命或控制他人编队；`NET-05` 服务器崩溃恢复、版本兼容、赛果幂等；`NET-06` 容量、网络预算、隐私及运营监控满足第22章。

## 17. 数据模型、公共契约与事务

### 17.1 定义、持久实例与临时实体

定义数据（`*Def`）由内容包提供，在会话中不可变；长期实例（`Hero`、`Party`、`Clan`、`Settlement` 等）只存储变化状态和引用；临时实例（`Agent`、`Formation`、`Projectile`、`SiegeDevice`）随 Mission 创建和释放。定义 ID 使用 `namespace:type/name` 稳定字符串，不依赖数组顺序或文件名；载入后可映射为紧凑整数索引。持久 EntityId 使用类型化的 64 位整数或 UUID；战场句柄为 index + generation，禁止跨 Mission 复用。存档引用必须可解析/迁移；定义移除时使用显式替代或拒绝载入。序列化禁止引擎 Node/RID、函数、线程对象及裸内存地址。

```mermaid
erDiagram

    CLAN ||--o{ HERO : members
    CLAN o|--o{ PARTY : owns
    CLAN ||--o{ SETTLEMENT : holds
    ARMY o|--o{ PARTY : gathers
    PARTY ||--o{ ROSTER_ENTRY : contains
    TROOP_DEF ||--o{ ROSTER_ENTRY : defines
    SETTLEMENT ||--o| MARKET : hosts
    MARKET ||--o{ STOCK_ENTRY : contains
    ITEM_DEF ||--o{ STOCK_ENTRY : defines
    ENCOUNTER ||--o{ RESERVATION : reserves

    TEAM ||--o{ FORMATION : commands
```

图为逻辑关系；并非数据库物理表。`Party` 可以不在 Army；未分配编队的 Agent（访客、动物等）允许 FormationId 为空，独立家族 KingdomId 可空；守军/民兵、无家族商队使用可选所有者和类型化来源。城堡/村庄可无完整市场，`SETTLEMENT`—`MARKET` 关系为 0..1。持久数据通常采用内存仓库和快照，不要求 SQL 才能实现单人。

### 17.2 关键实体字段（最小契约）

| 实体 | 核心字段 | 约束 |
|---|---|---|
| WorldState | world_id, schema_version, seed, game_minute, revision, rng_states, repositories | 每次提交 revision 单调增加 |
| Hero | id, def_id, clan_id?, birth_time, traits, skills, perks, relations, equipment_refs, location_ref, life_status | 只能有一个合法当前位置；死亡不可正常入队 |
| Clan | id, culture_id, leader_id, kingdom_id?, members, renown, tier, asset_refs, party_ids, fief_ids | leader 是合法在世成员，空位进入继承流程 |
| Kingdom | id, ruler_clan_id, member_ids, policy_ids, decision_ids, army_ids, treasury_id | 家族成员引用一致，灭亡后清理活动决议 |
| Party | id, kind, leader_id?, owner_ref?, pos, roster, prisoner_roster, inventory_id, account_id, morale, order | 兵力非负、合法阵营、预留计入可用数量 |
| Army | id, kingdom_id, leader_party_id, party_ids, target, cohesion | 成员最多参加一个军团，领导队伍属于成员 |
| Settlement | id, def_id, owner_clan_id, governor_id?, stocks, prosperity, loyalty, security, militia, garrison_ref, buildings, siege_id? | 地点固定、所有者合法、粮食及驻军非负 |
| Market | id, settlement_id, stock_by_item, demand_model, account_id, quote_revision | 金钱与货物事务一致，报价带版本 |
| Encounter | id, kind, participants, reservations, phase, revision, committed_result_id? | 每场最多提交一次，可回滚未提交预留 |
| QuestInstance | id, def_id, def_version, actor_refs, stage, deadline, counters, status, rewarded | 终态与奖励幂等 |
| MissionState | id, ruleset_id, tick, teams, entity_store, objectives, spawn_state, result_builder | 临时状态独立，无直接世界写入 |
| Formation | id, team_id, controller, member_handles, order, layout, slots, morale | 一名战斗单位至多归一支编队 |
| Agent | handle, source_slot, team_id, formation_id?, transform, health, equipment, action, mount_link?, status | 句柄有效、来源唯一、生命状态合法 |

### 17.4 跨域接口（语言无关伪代码）

```text
EncounterSpec {
  schema_version, encounter_id, reservation_revision, mode,
  scene_def_id, ruleset_id, environment, rng_seed,
  sides: [{ team_key, faction_id, commander_hero_id?, roster_allocations }],
  reserved_sources: [{ source_party_id, troop_def_id?, hero_id?, count,
                       source_slot_range, loadout_snapshot_id }],
  battle_limit, deployment_constraints, siege_snapshot?
}
MissionResult {
  schema_version, result_id, encounter_id?, mission_id, reservation_revision?,
  outcome, duration_ticks, winner_team_keys[], objective_results[],
  slot_outcomes: [{ source_slot_id, end_status, wounded, captor_team_key?, xp }],
  loot_claims[], hero_outcomes[], siege_changes?, reward_intents[], stats, integrity_hash
}
FormationOrder {
  mission_id, order_id, issuer_id, client_sequence, issued_tick,
  formation_ids[], order_type, target_position?, target_formation_id?, parameters
}
CommandReceipt { command_id, status, committed_revision?, errors[], view_changes[] }
```

`source_slot_range` 用于大规模批次的紧凑编码；Hero 槽 count=1；MissionResult 可以对结果相同的普通兵槽位范围压缩，但不能丢失去重、归属及总量验证能力。`integrity_hash` 用于检测一致性/损坏，不等于安全签名；多人结果需经认证服务端身份签名/验证。不同模式用独立 ResultRouter，战役结果包含 Encounter 关联，自定义/多人不可提交战役命令。

### 17.5 关键命令与事件清单

| 命令 | 权威处理器 | 已提交事件 | 主要失败条件 |
|---|---|---|---|
| MoveParty / SetTimeScale | World/Session | PartyDestinationChanged / TimeScaleChanged | 目标不可达、暂停锁定 |
| BuyGoods / SellGoods | Economy+Ledger 事务 | GoodsTraded | 报价过期、钱/库存不足 |
| Recruit / Upgrade / TransferTroops | Party | RosterChanged | 无名额、资源不足、参战预留 |
| AssignRole / EquipHero | Character+Clan/Inventory | RoleAssigned / EquipmentChanged | 人物不可用、槽位不符 |
| CreateArmy / JoinArmy | Party/Army | ArmyCreated / MemberJoined | 关系/权限/影响力不足 |
| ProposeDecision / Vote | Politics | DecisionProposed / VoteRecorded | 非成员、过期、重复 |
| DeclareWar / MakePeace | Diplomacy | WarDeclared / PeaceSigned | 非法状态、未获授权 |
| BeginEncounter / StartSiege | Encounter | EncounterReserved / SiegeStarted | 双方无效、重复遭遇 |
| CommitEncounterResult | Encounter+业务事务 | EncounterSettled + 分项事件 | ID/版本冲突、兵力不守恒 |
| IssueFormationOrder | Mission/Formation | OrderAccepted（或轻量回执） | 控制权、目标、状态无效 |
| AcceptQuest / CompleteDialogueChoice | Quest/Dialogue + 用例 | QuestAccepted / DialogueResolved | 前置条件变化、实体无效 |
| SaveGame / LoadGame | Session/Persistence | SaveSucceeded / WorldLoaded | 非安全点、校验失败 |

跨模块事务示例：`BuyGoods` 校验报价 → 原子扣买家资金/卖家库存 → 增卖家资金/买家库存 → 写流水 → 提交 revision → 发布事件。采用单权威线程内写入集/变更日志或可回滚事务，避免每次复制整个世界。战斗结算是较大事务，应先计算并验证所有变更集，随后一次提交，并将结果 ID 与状态持久化；失败仍保留待结算结果。

## 18. 存档、数据包、MOD 与配置管理

### 18.1 存档格式与恢复

```text
save/<slot>/
  manifest.json        # 格式/游戏版本、内容包与版本、世界 ID、时间、校验、显示摘要
  world.bin            # 世界状态快照（版本化序列化，支持压缩）
  transactions.bin     # 可选，关键提交/未完成遭遇恢复日志
  thumbnail.webp      # 可选，不影响存档有效性
  backup/             # 最近安全版本或独立备份槽
```

存档在 tick 屏障取得不可变快照，后台编码/压缩/写临时文件，完成后校验并原子替换提交标记（按平台支持的文件持久化语义实现）。保留上一有效版本；失败不覆盖旧存档。定时/手动/关键事件自动存档采用同一机制，暂停时间不与文件 I/O 竞争。战役默认仅允许安全点保存；战场使用进入前检查点、待提交结果日志和退出/崩溃恢复策略，而不承诺任意战斗帧中途存档。铁人模式限制手动回滚但仍需故障恢复。

必须保存：世界时间与随机流、英雄/关系/谱系、家族/王国/队伍/库存、地点/市场、战争/围城、任务阶段、动态物品定义、AI 长期计划、待处理事务与结果去重记录、模组清单；可重建：导航缓存、视觉资源、UI 临时状态、空间索引、战场动画节点。迁移采用 `vN → vN+1` 顺序纯数据变换，备份原始文件，校验引用/枚举/资产。未知关键字段与不兼容模组不得静默丢失。用户可读取存档失败原因及建议操作。

### 18.2 内容加载与 MOD

```text
package/
  manifest.json        # id, version, requires, conflicts, load_after, game_api_version
  definitions/         # 数据定义及规则参数
  patches/             # 显式增量变更
  scenes/              # 地形/任务场景
  assets/              # 模型、动画、音频、材质
  localization/        # 语言键与翻译
  scripts/             # 受支持的扩展接口（可选）
```

加载顺序：扫描 → 解析 manifest → 依赖拓扑排序 → 版本/冲突验证 → 定义合并/补丁 → 引用和规则校验 → 编译快照/内容哈希 → 注册扩展 → 创建世界。补丁使用稳定定义 ID 和明确 add/replace/remove 操作，冲突给出两个包的来源；同一世界定义不可热修改破坏存档，游戏内编辑数值仅在明确调试模式使用。扩展注册点包括世界行为、规则模型、任务目标、对话条件、Mission 规则、编队行为、战术策略与 UI 扩展；禁止依赖内部类和反射修改私有数据。

配置覆盖优先级明确（基础规则→资料片→模组依赖顺序→世界开局修饰器→单人玩家合法选项），记录最终生效来源。多人由服务端固定内容清单和哈希，客户端仅允许匹配或白名单纯外观包。数据型 MOD 默认安全校验路径、资源大小、引用循环；代码 MOD 若可执行任意本地代码不能宣称沙箱安全，需显式信任提示、禁用不可信代码和单独兼容测试。发布包提供许可证、API 版本与变更说明；不捆绑未经授权的原作资源。

### 18.3 验收

`SAV-01` 完整世界保存/载入、长期运行与多槽；`SAV-02` 崩溃/磁盘满/损坏回退、结算幂等；`SAV-03` 版本迁移、动态物品、缺失模组可解释；`EXT-01` 新增文化、兵种、物品、场景、规则/行为、任务不修改核心；`EXT-02` 加载顺序、冲突、多人哈希校验与禁用危险扩展；`EXT-03` 内容验证、发布与版本化 API。

## 19. 引擎实现、性能与线程模型

### 19.1 技术选型（新项目独立决策）

候选引擎 Godot 4.x、Unity、Unreal 或自研引擎均可实现总体边界。为便于给出可实施的工程规格，本文提供 Godot 4.x 落地方案；选择具体稳定版本应由 500/1000 人压力实验、动画/蒙皮、导航及工具链验证决定，不承诺仅凭选用引擎即可达到目标。

| 能力 | 建议实现 |
|---|---|
| 业务领域、应用、UI、规则 | 类型化 GDScript 或 C#；团队应统一主要语言，领域测试不依赖场景节点 |
| 热路径（感知、编队、碰撞候选、批量模拟） | 优先优化算法与数据布局；经 profiler 证明瓶颈后使用 C++ GDExtension，批量接口避免逐 Agent 跨语言调用 |
| 表现与场景 | Godot SceneTree、PackedScene、AnimationTree、材质/资源系统、输入、音频 |
| 导航/物理 | 引擎 NavigationServer、PhysicsServer 或自定义适配器；基于压测选择代理数、动态区域和批量策略 |
| 大量实体渲染 | 网格/材质合批、空间分块、实例化、骨骼动画 LOD；MultiMesh 用于适合的重复网格或定制动画渲染，不默认解决每名士兵独立骨骼蒙皮 |
| 联机 | 专用 headless 构建、权威命令与快照协议；可采用 ENet/UDP 传输及可靠通道，平台鉴权另接入 |
| 数据/工具 | JSON/CSV/Resource 作为编辑输入，编译成验证后的版本化运行时数据；编辑器插件、CLI 校验与 CI |

不强制从第一天采用 C++、ECS 框架或完全自研引擎。对象式领域模型适合长期世界和规则；战场高频状态适合 SoA 数据布局/批处理，两者混合。GDScript 编排、C# 或 C++ 热点加速均需测试行为一致；不要在多个语言层维护不同战斗真值。若 Godot 在所需蒙皮或物理容量上不达标，可替换 EngineAdapter 而不重写角色、经济、政治规则；实时战场后端替换仍会有实现成本。

### 19.2 线程与调度

```mermaid
flowchart LR
    A[主/权威模拟线程: 快照与输入] --> Q[任务队列: 感知/评分/路径请求]
    Q --> W1[Worker 1]
    Q --> W2[Worker 2]
    Q --> W3[Worker N]
    W1 --> B[意图/结果缓冲]
    W2 --> B
    W3 --> B
    B --> C[同步屏障: 校验/稳定合并/提交]
    C --> R[表现快照/网络增量]
    C --> A
```

采用一个权威写入顺序、多个计算工作线程。AI 工作读取不可变快照，输出 `{tick, entity_handle, intent}`，不直接写 SceneTree 或权威组件。移动/伤害阶段可按独立批次并行候选生成，但全局碰撞与跨实体结果需确定合并顺序。Godot 的活动场景树不是线程安全的；资源/引擎服务器接口需遵守所选版本线程安全和同步说明。导航服务器变更可能在后续同步阶段生效，查询须带 nav_revision；不能假设刚开门同一帧路径已经更新。避免在持锁期间调用外部脚本；任务按 Mission 取消令牌和 deadline 退出，卸载场景先等待/取消所有作业。存档编码和资源加载使用快照或隔离队列。

### 19.3 性能分级与复杂度

| 子系统 | 优化路线 | 禁止事项 |
|---|---|---|
| 战场感知 | 空间哈希/网格、有限近邻、遮挡分批 | 每 Agent 遍历全场敌人 O(N²) |
| 路径规划 | 编队共享路径、队列预算、局部避障、版本缓存 | 每帧每兵全图寻路/全图重烘焙 |
| 动作/碰撞 | 紧凑组件、扫掠候选粗筛、碰撞层、近战优先 | 所有士兵全刚体全骨骼检测 |
| AI | 分层频率、错峰、按重要度 LOD、任务池 | 每帧全层级更新或为每兵创建线程 |
| 渲染 | 视锥/遮挡、材质合批、动画/骨骼 LOD、阴影距离、实例化 | 全员最高精度骨骼/阴影/独立材质 |
| 音频/特效 | 优先级、池化、距离衰减、数量上限 | 每命中无限音源/粒子/尸体 |
| 战役 | 分相日结、聚合 roster、事件驱动索引 | 地图上每兵创建实时节点 |
| UI | 虚拟列表、增量 ReadModel、事件合并 | 每帧重建百科/库存/所有面板 |

性能 LOD 与战斗规则分开：视觉可降低刷新、阴影和骨骼精度；AI 可降低非紧急决策频率，但权威生命、目标和伤亡不能因为摄像机转向而无故改变。单人低配置可调整同屏兵力及表现预算；多人由服务器统一规定实际规则，不允许客户端降低实体数量改变战果。

### 19.4 性能预算与设备假设

建议基准机：桌面 8 核现代 CPU、32 GB RAM、中端独显（8 GB 显存）、SSD，1080p 中画质。实际测试需记录具体型号、驱动、引擎版本和场景内容。500 人野战含混合步/骑/远程为默认 60 FPS 目标；1000 人为 30 FPS 以上压力目标。城堡攻守另测狭窄地形、动态导航、器械、骨骼和弹体峰值。不得用静止无动画单位代替实际战斗压力。

| 指标 | 初始验收目标（待性能基线确认） |
|---|---|
| 500 人战场 | 95% 帧时间不高于 20 ms；平均至少 60 FPS，1% low 另记录 |
| 1000 人压力战场 | 95% 帧时间不高于 40 ms；平均至少 30 FPS，无持续模拟积压 |
| 战场 CPU | 固定 tick 主路径 95% 低于步长，慢帧可有限追赶；不丢弃权威命中/伤亡 |
| 战场 GPU | 60 FPS 档以 16.7 ms 为帧目标；CPU/GPU 并行测量，不简单相加 |
| 战役快进 | 300–500 地点、2000–5000 队伍规模持续推进，无明显 UI 卡死；日结分片 |
| 资源 | 客户端 RSS 初始目标 ≤ 10 GB；显存预算 ≤ 7 GB（8 GB 卡），按画质降级 |
| 载入 | SSD 普通场景从确认到可操作 P95 ≤ 15 s；大型攻城 ≤ 25 s |
| 专用服务器 | 约定玩家/AI 容量下 P95 tick 低于预算、无持续积压或断线尖峰 |
| 稳定性 | 连续 50 次 Mission 切换无单调内存增长；8h 战斗循环与长期战役仿真 |

60 FPS、加载时间等均为设计指标，不能作为已实现性能。GPU 主要影响渲染/动画，AI、导航、碰撞与战略模拟常受 CPU 和内存带宽限制。建立 per-system profiler、tick 火焰图、路径请求队列、活跃实体/蒙皮数、GPU draw/帧时间、存档大小与网络吞吐指标；每次内容规模提升重复测量。

### 20.2 依赖与开发契约

```text
bootstrap -> application, infrastructure, presentation, campaign, mission, multiplayer
presentation -> application public ports, contracts
application -> campaign public interfaces, mission public interfaces, contracts
campaign/mission -> shared, core, contracts, local ports
infrastructure -> implemented ports, contracts, engine/platform SDK
shared/core/contracts -> no campaign, mission, presentation or engine scene dependencies
```

模块内部跨域引用通过 public facade/接口；编译器或 CI 静态检查禁止反向依赖与循环。引擎节点只能在 adapter/presentation 或明确场景层；核心规则可独立运行。日志含 world/mission ID、tick、entity、command/result ID，避免默认记录隐私。代码规则：类型与单位明确；公共接口有失败语义和副作用文档；随机流注入；不在 UI/动画回调中修改权威状态；热路径避免临时分配；边界变更必须更新契约、迁移与测试。

### 20.3 Git、构建与 AI 辅助开发

版本控制采用 Git；大型二进制用 LFS 或资产仓库，禁止将导入缓存、构建输出和用户存档提交源仓库。CI 产出 PC 客户端、专用服务器、数据包、符号/崩溃映射、版本与内容哈希；保留可复现构建脚本，依赖锁定、许可证清单、发布签名与回滚流程。

每个模块提供 README：职责、所有权、公开接口、依赖、数据结构、事件、测试、性能预算、不允许的行为。开发任务（含 AI 编程）必须引用需求 ID、限定可修改目录、声明契约变更、提供单元/集成验收；跨模块变更写架构决策记录 ADR 并人工评审。禁止让生成式 AI 自行引入第二套 Session、事件总线、经济模型或重写既定公共类型。AI 生成代码的正确性以测试和审查为准，不以代码生成速度为完成度。

| AT-17 | 海上运输—战斗—占领—舰队/战役回写（扩展） | 船舶、船员、港口与货物一致，旧本体存档有迁移策略 | NAVAL（EXT） |

### 22.3 长期仿真质量与平衡

以至少 20 个固定种子和若干随机种子运行 1/3/10 游戏年。硬门槛：零非法负库存、零重复英雄身份、零参战预留泄漏、零无主且未处于合法过渡态的领地、零无法解释的货币/兵力变更。软指标经基线确定：总货币与商品库存增长趋势、主要食品可获得性、物价区间、城镇繁荣/忠诚分布、王国战争时长、家族消亡率、新英雄成年率、商队存活率、AI 计划抖动。观察少数势力扩张与经济衰退是合理涌现，不强制所有王国永久平衡；需要避免所有地图在短期内同质化、完全饿死、无兵或永久无法议和。

自动战斗与实时战斗使用同兵种、地形、数量与统帅配置做批量统计，对胜率、伤亡、溃逃、兵种克制进行置信区间比较。以代表性场景的误差阈值评审，不用单局相等作为目标。AI 公平性测试记录其读取的快照权限、合法命令与资源来源；测试难度改变是否超出配置。性能门禁以同设备、同内容、同镜头轨迹和随机种子运行多次，报告 P50/P95/P99、最差帧、单位数、CPU/GPU、内存、网络。超过基线回归阈值（建议 10%）必须分析并评审，不能只降低单位数掩盖问题。

## 23. 完整研发计划与交付标准

### 23.1 实施原则

本章是实现顺序，不是产品缩减计划。每一阶段交付并验证真实可复用的能力，后续阶段在同一正式架构内增加功能。优先解决高风险基础设施（战斗容量、骨骼动画、导航、持久化一致性、多人权威），避免完成数百张地图之后才发现底层性能不达标。内容生产可与程序并行，但在骨架、场景标记和数据契约冻结后批量扩展。

| 阶段 | 完成的正式系统与可验证里程碑 | 前置条件/门禁 |
|---|---|---|
| P0 架构和技术验证 | 引擎选型、数据/命令/存档契约、动作原型、500/1000 单位真实压力、NavMesh 瓶颈、专用服务器验证 | ADR、基准报告；未达到容量则调整技术方案 |
| P1 公共运行时 | Session、时钟/随机、定义编译、仓库/事务、测试框架、Mission 生命周期、视图/引擎适配 | 无循环依赖，纯领域可测试，最小存档可迁移 |
| P2 实时战争 | 完整方向战斗、弓弩/骑乘、编队、战术/个体 AI、部署/增援、野战和结果 | COM/BAT/BAI/NAV 功能与性能门禁 |
| P3 战略与角色 | 世界地图、队伍、家族成长、库存/后勤、遭遇和自动战斗、持久化 | AT-01/05/09/10，世界与战场正式契约 |
| P4 社会仿真 | 经济/商队/工坊/锻造、领地、政治/外交、战略 AI、围城与攻城 | AT-02/03/06/08/14，长期仿真稳定 |
| P5 完整单人内容 | 剧情、动态任务、对话、竞技/访问/藏身处/潜入、自定义战斗、全部主要 UI | MOD-01/02/03 和 AT-07/16，全流程无阻断 |
| P6 多人和扩展工具 | 专用服务器、全部模式、匹配/重连/管理，MOD SDK、编辑器和发布包 | NET/EXT 全部验收与安全/容量测试 |
| P7 内容扩量与发布 | 原创全地图、兵种树、资产、剧情、音频、本地化、平衡、回归、安装/更新/存档兼容 | 全量 MUST 需求完成，QA/性能/授权/发布评审 |
| P8 独立扩展 | 海战与后续扩展，通过公开模块接口接入完整本体 | NAVAL 全部验收；不破坏本体存档/规则 |

联网协议与热路径容量在 P0 验证，公共规则从 P1 起面向权威运行，不等到 P6 才改造。存档从 P1 持续演进；MOD 和工具的公共接口从 P1 定义、P6 完成面向用户的工具交付。P3/P4 可并行推进独立领域，但结算与账本契约须先稳定。

### 23.2 工作量与角色分工

完整同类商业游戏是大型、多学科、长周期项目，远非一个战斗脚本或单一程序员短期可完成。主要工作流：产品/玩法和数值设计；核心架构与工具；动作/物理/AI/导航；战略/经济/政治/任务；UI/输入/可访问性；3D 角色/场景/动画/特效/音频；多人/在线/安全；QA/自动化与发布。独立小团队可以降低原创资产数量、选择授权资产和工具，但完整功能范围仍需逐项实现，不能将估计当作确定工期。

每个工作包交付：详细设计（状态、算法、公式、依赖、接口）、代码、配置/资源、单元/集成测试、调试指标、用户交互、性能验证、版本/迁移说明。优先级以依赖和风险排序，不以“做过演示”替代正式实现。内容规模在 P0/P1 结合预算冻结；先建立生产基线，按实际产出速率和缺陷率估算后续计划。研发管理使用需求 ID → epic → story → 实现/数据 → 验收证据的追踪链。

### 23.3 发布定义（Definition of Done）

- 所有 MUST 需求均在追踪表有负责人、实现、测试及通过证据；EXT 独立标识，不能将本体缺失模块降为 EXT 来宣称完成。
- 完整单人、剧情、沙盒、自定义战斗、多人和 MOD 工具可独立使用，模式间状态隔离；玩家能在同一战役中经历从创建人物到家族/王国发展和传承的完整循环。
- 已通过跨模块事务、保存恢复、长期仿真、战斗/攻城性能、多人安全与故障测试；没有阻断主流程、损坏存档、复制资产或非法控制权的已知严重缺陷。
- 原创内容/授权审计完成，全部正式场景通过导航、出生、目标、资产预算及本地化检查；支持安装、版本升级、卸载及故障报告。
- 完整功能对标以测试场景和功能矩阵验收，不以目录已创建、类名与原作相似或 UI 已搭建为依据。任何尚未实现能力明确列出而非宣称完全复刻。

## 24. 完整海战扩展设计（独立内容包）

海战对应参考游戏的独立资料片能力，属于额外完整产品范围，而不是本体陆战的一个地图变种。陆战架构须从第一版允许可移动战斗平台、跨地形通行、复合目标、不同任务规则和扩展定义；具体海战实现按独立里程碑交付。

### 24.1 战略层：海域、港口、舰船与舰队

新增 `WaterRegionDef`、`PortDef`、`ShipDef`、`ShipInstance`、`Fleet`、`SeaRoute`、`Shipyard`。世界图支持陆路/河流/近岸/远海的交通边，通行能力由舰船吃水、港口与天气决定；队伍登船或登陆是库存、乘员与位置的原子转移，不能在陆地和舰队中重复出现。舰队由多个船舶实例组成，拥有船长、成员队伍、船员、补给、运载/货仓容量、航行速度与目标。舰船损伤、升级、载货、船员岗位和所有权持久化；船坞可建造、购买、维修、出售和更换部件，交易依赖真实材料、时间和资金。舰船捕获必须校验船员、容量和回港能力。

风向/风速、海流、水深、天气、季节、帆/桨推进影响航速、风险和路线成本。海上商队/海盗、海上军团、港口封锁、海运贸易、沿岸/河流劫掠与两栖登陆通过战略 AI 和 Encounter 接入；港口开放、封锁与船坞产能影响货物供应。海员招募、航海技能、船队职责、海上补给与船员士气复用 Character/Party/Economy 规则，在扩展中添加可配置效果。

### 24.2 实时层：舰船作为可移动局部战场

`NavalMission` 组合现有 Agent、Combat、Formation 与新增 `ShipRuntime`、`SeaEnvironment`、`NavalMovement`、`Boarding`、`ShipDamage`。每艘船为可运动参考系，船上角色保留局部坐标并计算世界位姿；甲板 NavMesh 在船局部空间查询，转换到世界坐标处理射击、交互和跨船移动。船体碰撞、浮力、风浪、转向、航速、桨/帆、船体与部件伤害由权威系统处理；不要求完整流体模拟，采用经校准的简化浮力和环境模型。

舰船状态：正常航行、接近/保持距离、接触、挂靠、登船、失控、沉没/撤离。撞击、船体漏损、桨/帆损坏、火力武器、乘员伤亡与投降分别有规则；船沉后船员按明确的逃生/伤亡/救援规则处理，不能因删除船节点直接删除参与槽位。跨船 NavLink 仅在船距、相对速度、朝向和连接状态符合条件时启用，并支持断开时的安全恢复。登船位置、船舱、甲板高差、攀爬、掉落、水中状态与摄像机都纳入导航/动作测试。

玩家可亲自操船或委派舰长、指挥舰队、操作器械、射击、接舷和带队交战。海战 AI 层级仍为战术（舰队目标）、舰船/编队（路线、队形、接舷、火力）、个体（岗位、战斗、登船）；其候选目标遵守真实风浪、船体状态、航向、速度和可达性。舰队 AI 具备规避碰撞、择机接近、控制距离、保护受损船、撤退等游戏策略。海战与陆战均复用权威动作与目标系统，但海上移动、视野与导航采用专用适配器。

### 24.3 跨域数据契约

```text
NavalEncounterExtension {
  fleet_ids[], ship_allocations[], sea_region_id, weather_seed,
  wind, current, port_or_coast_context?, boarding_ruleset_id
}
ShipAllocation {
  ship_instance_id, source_fleet_id, team_key, damage_snapshot,
  equipment_snapshot, crew_source_slots[], cargo_manifest
}
NavalResultExtension {
  ship_outcomes: [{ ship_instance_id, status, damage, captured_by_fleet_id? }],
  cargo_transfers[], crew_slot_outcomes[], port_changes?, naval_xp[]
}
```

这些是 `EncounterSpec` / `MissionResult` 的版本化扩展，不另开一套持久化战斗提交机制。陆战结果读取器不应误处理船舶字段，启用海战的世界必须使用相应内容包；关闭扩展/移除船舶数据时提供显式迁移或拒绝载入，不能默默抛弃玩家船只和船员。

### 24.4 内容、工具与验收

海战交付包含新的原创文化/地区、船型与船舶部件、海员兵种、武器装备、技能、港口、海上贸易和海盗事件、引导剧情、河流/海岸/开放水域场景、自定义海战。船舶编辑器验证局部导航、甲板碰撞、武器挂点、上下船点、船员槽、船体物理与沉没状态；水域地图编辑器验证陆海连通、港口、航线、吃水和海图；海战性能另外评估移动参考系、波浪、动态船只与大量船员。

`NAVAL-01` 陆海移动、港口、舰船买卖/建造/维修/装备与舰队所有权；`NAVAL-02` 海上贸易、海盗、补给、封锁及两栖袭击；`NAVAL-03` 海战操船、风浪、碰撞、部件损伤、火力与接舷；`NAVAL-04` 动态跨船导航、船员 AI、撤离与沉没；`NAVAL-05` 海战伤亡/船舶/货物一致结算、存档与迁移；`NAVAL-06` 海上剧情、原创地区/兵种、海战编辑器与自定义战斗；`NAVAL-07` 扩展不破坏陆战核心或未启用扩展的本体世界。

### 25.2 高风险与应对

| 风险 | 影响 | 缓解/触发条件 |
|---|---|---|
| 大规模 AI、蒙皮与碰撞超预算 | 战斗规模和操作体验无法达到对标目标 | P0 用真实混合战场压测；热点数据导向/原生扩展；不达标时重新评估引擎/渲染方案 |
| 大量个体在城门/楼梯拥堵 | 攻城无法完成 | 编队共享走廊、局部 NavLink、瓶颈与拥堵基准；场景验证门禁 |
| 经济或政治长期崩溃 | 沙盒不可持续 | 多种子十年仿真、库存/账本/资源来源校验、平衡反馈与审查 |
| 战役/战场结算重复或丢失 | 存档损坏、资源复制 | 预留、唯一来源槽、幂等结果、原子提交与故障注入 |
| 动画与命中不同步 | 手感差、多人争议 | 权威动作窗口、碰撞扫掠、资产标记验证、延迟补偿实验 |
| 多人带宽/延迟/作弊 | 模式不稳定或不公平 | 权威服务器、增量与兴趣管理、网络故障测试、审核与运营 |
| 内容数量远超制作能力 | 正式产品无法达到完整体验 | 原创模块化场景、美术规范、工具与可验证产量，优先冻结生产基线 |
| 模组与版本不兼容 | 存档及服务器崩溃 | 版本化 API/manifest、明确迁移、内容哈希、信任边界 |
| 模块间循环依赖与 AI 生成代码失控 | 系统难以维护和扩展 | 数据所有权、契约测试、依赖检查、代码评审和 ADR |
| 未经授权使用原作内容 | 发布/发行风险 | 独立设定、美术、音频、代码及规则表；记录授权来源，发布前审计 |

### 25.3 首批架构决策记录（ADR）

| ID | 决策 | 理由 / 重新评估触发 |
|---|---|---|
| ADR-001 | 模块化单体，独立 Campaign/Mission 运行时 | 降低分布式复杂度，保证世界与战斗数据边界；多人服务独立部署 |
| ADR-002 | 持久世界与临时战场实体分离 | 大世界容量、稳定存档、战役/自定义/多人共享战斗 |
| ADR-003 | 权威单写入与命令/快照/事件 | 避免竞争和重复真值；若热点出现则调整数据布局/批处理，不改变所有权 |
| ADR-004 | 混合对象模型与数据导向战场 | 长期业务与高频模拟有不同访问特征；以 profiler 决定原生热点 |
| ADR-005 | 战术—编队—个体分层，统一指挥接口 | 玩家与 AI 共享命令语义，减少耦合，便于新战术扩展 |
| ADR-006 | 单人本地权威，多人专用服务器 | 共享规则、保护多人真值、避免全物理跨平台锁步 |
| ADR-007 | 版本化配置/存档/MOD，稳定 ID | 支持内容扩展、迁移和多人兼容验证 |
| ADR-008 | 引擎无关领域 + Godot 候选适配 | 以容量和开发工具验证选型；引擎不进入持久领域模型 |
| ADR-009 | 原创世界与资产，功能对标不复制内容 | 支持独立发布，并避免将原作数据写死为系统要求 |
| ADR-010 | 海战独立扩展包 | 复用世界/战斗/结算契约，避免陆战架构硬编码静态地面平台 |

## 最终架构结论

整款游戏不是围绕“战斗场景”构建，而是围绕**长期世界仿真与局部实时仿真之间的稳定契约**构建。玩家与 AI 是不同控制器，不是两套玩法；政治、经济、家族和军队通过正式领域模型互相作用；所有战斗与访问形式由可组合 Mission 规则产生；数据、工具、存档、联网和内容生产是正式系统，而不是最后追加的附属功能。

本文件作为完整项目的统一总体设计基线。进入开发前应冻结首批 ADR、版本化数据契约、引擎性能基线、原创内容规模和需求追踪矩阵；各模块根据本文继续形成详细设计与测试，并在同一个整体架构内实现全部交付项。
